## Chapter 4: Model Deployment Architectures and Production Controls — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Shadow deployment — what happens to its output? | Model runs in parallel on live production traffic but output is logged/compared only — never returned to users or downstream systems. Exam tip: shadow = zero user impact by design. |
| 2 | Canary deployment — core mechanism? | Incrementally route a small, growing percentage of real traffic to the new version while monitoring metrics; enables fast, low-blast-radius rollback. Exam tip: canary = gradual exposure, not instant cutover. |
| 3 | Blue-green deployment — core mechanism? | Two full parallel environments (old='blue', new='green'); traffic is switched entirely at cutover, enabling near-instant rollback by switching back. Exam tip: full switch, not gradual. |
| 4 | HTTP status code returned when a client exceeds an API rate limit? | 429 Too Many Requests. Exam tip: distinguish from 401 (auth failure) and 403 (authorization/forbidden). |
| 5 | Token bucket vs leaky bucket rate limiting — key difference? | Token bucket allows bursts up to bucket capacity then refills at a steady rate; leaky bucket enforces a strictly constant outflow rate regardless of burst. Exam tip: token bucket = burst-tolerant; leaky bucket = smooths to constant rate. |
| 6 | Common API gateway authentication methods for model endpoints? | API keys, OAuth2/OIDC tokens, and mutual TLS (mTLS). Exam tip: mTLS provides strongest mutual identity assurance for service-to-service calls. |
| 7 | Edge deployment vs embedded deployment — difference? | Edge = model runs on local/on-premises hardware near the data source (e.g., gateway device, local server); Embedded = model is compiled directly into a device's firmware/application with no separate serving layer. Exam tip: embedded implies tighter resource constraints and no network dependency at all. |
| 8 | Batch deployment vs real-time deployment — when to choose which? | Batch: scheduled, high-volume, latency-tolerant scoring (e.g., nightly risk scores). Real-time: synchronous, low-latency, per-request inference (e.g., fraud check at checkout). Exam tip: exam gives a latency/volume scenario — match the pattern to the tolerance stated. |
| 9 | Change management requirement before a production model update ships? | Documented validation (performance + bias/fairness testing), independent risk/compliance sign-off, and predefined rollback criteria — before deployment. Exam tip: self-approval by the model's own dev team violates segregation of duties. |
| 10 | Typical rollback trigger metrics for a canary release? | Error rate spike, latency/SLA breach, prediction/data drift beyond threshold, or business KPI degradation. Exam tip: rollback criteria must be defined BEFORE rollout begins, not decided reactively. |
| 11 | Key vendor-hosted model risk control beyond a standard NDA? | Contractual right-to-audit clause plus ongoing access to change logs/incident reports. Exam tip: NDA protects confidentiality only — it gives no operational assurance over time. |
| 12 | Best capacity-planning metric for AI inference autoscaling (vs generic web apps)? | Request queue depth / inference latency (and GPU utilization where applicable) — not CPU utilization alone. Exam tip: CPU-only scaling policies commonly fail to catch inference-specific bottlenecks like batching/queue wait. |
